# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm test` — run the full Vitest suite
- `npx vitest run test/rules.test.js` — run a single test file
- `npm run dev` — local dev server (`wrangler dev`; `predev` auto-applies migrations to local D1). Starts with an EMPTY local database — populate it explicitly with `npm run seed`.
- `npm run seed` — populate the local D1 by running the Deno offline discovery batch against local D1 (`deno run --allow-net --allow-read --allow-write scripts/discovery-batch.js --out ./.seed.sql --no-classify && node scripts/apply-local-sql.js ./.seed.sql`). The apply goes through `scripts/apply-local-sql.js`, which splits the delta into <90 KB line-aligned chunks — `wrangler d1 execute --local --file` hands the whole file to workerd as ONE SQL call, capped at 100,000 bytes (`SQLITE_TOOBIG`), and a full delta is ~700 KB; the workflows' `--remote` apply uses the D1 import API and is NOT affected. Hits the live Overpass API and takes ~2 minutes; run it once per fresh database, not on every dev start. `--no-classify` skips water-body classification for speed; use `npm run seed:classify` to run the batch WITH classification. `npm run seed:enrich` (NWS point enrichment, 75 beaches/run — repeat to drain the queue), `npm run seed:eccc` (ECCC zone enrichment for Canadian rows NWS has parked), `npm run seed:webcams` (Windy webcam hydration), `npm run seed:waves` (6-hourly wave refresh, cron `15 */6 * * *` — populates the `waveinput:`/`waves:` KV the flag recompute reads), and `npm run seed:flags` (hourly flag recompute) trigger the other crons the same way. `npm run seed:marine` is NOT a cron trigger — `beaches.marine_zone` moved to the offline batch, so it snapshots local D1 (`SELECT id, lat, lon, nws_zone, marine_zone FROM beaches`), runs `discovery-batch.js --no-discovery --no-classify --marine-zones data/marine-zones-greatlakes.json --snapshot <file>`, and applies the delta via `apply-local-sql.js`; run it AFTER `seed:enrich` has stamped `nws_zone` (the pass only derives zones for rows that already have one). Run `seed:waves` before `seed:flags` so the recompute has wave inputs to read.
- Cron triggering in local dev goes through `/cdn-cgi/handler/scheduled?cron=<urlencoded cron>`.
- `npm run deploy` — deploy (`wrangler deploy`); `npx wrangler deploy --dry-run` to validate config without deploying
- `npx wrangler d1 migrations apply swim-report --local` (dev) / `--remote` (production) — apply `migrations/` to D1
- Wrangler auth: there is no `wrangler login` session on this machine — export `CLOUDFLARE_API_TOKEN` from the `CLOUDFLARE_TOKEN` value in `.dev.vars` before any wrangler command that talks to the Cloudflare API (deploy, remote migrations, secrets, tail).

## Production

Live at **https://swim.report** (custom-domain route). `wrangler.toml` carries the real D1/KV IDs plus observability (full head sampling), Smart Placement, and a pinned `compatibility_date` (bump occasionally). The `WINDY_WEBCAM_API_TOKEN` Worker secret is set. Remote data populates via the crons only — there is no remote `npm run seed`; the request path serves whatever D1/KV currently hold.

`npm install` needs both `WEBAWESOME_NPM_TOKEN` and `FONTAWESOME_NPM_TOKEN` exported in the environment (values in `.dev.vars`, which is gitignored) — `.npmrc` routes `@web.awesome.me`/`@awesome.me` and `@fortawesome` through private registries via `${VAR}` placeholders; never hardcode a token in `.npmrc`.

## Mandatory JavaScript style

All project source and tests are plain JavaScript (no TypeScript), ES modules, and:

- `const`/`let` only, never `var`
- String concatenation with `+`, **never template literals** — no backticks anywhere
- `console.log` for logging

## Architecture

Single Cloudflare Worker (`wrangler.toml`, modules syntax) that **estimates** beach hazard flag status (green / yellow / red / double-red / unknown) for US beaches. The core product constraint: estimated conditions must never be presentable as official flag status — every payload carries `official: true|false` and the UI renders them distinctly (badges, footer disclaimer).

**PLAN.md is the authoritative contract** — exact D1 schema, KV shapes, module signatures, rules precedence, and reason-string formats. Update it when changing any cross-module interface. README.md documents the public API and rules table; TODO.md tracks known gaps.

### The two-path rule (never violate)

1. **Request path** (`fetch` → `src/router.js` → `src/frontend/render.js`): reads **only** D1 and KV. No upstream `fetch()` may ever be reachable from here.
2. **Cron path** (`scheduled` in `src/index.js`, dispatched on `controller.cron`): all upstream fetching happens here, split across independent triggers so one upstream's failure or rate limit never starves another. Beach discovery and water-body classification are NOT here — they are owned solely by the GitHub Actions offline batch (see the Offline path below).
   - `"7 * * * *"` (hourly): reads beaches from D1 — ordered hot-first (beaches with a `last_viewed` demand stamp within `HOT_VIEW_WINDOW_MS`, 7 days, always fully covered every run) then oldest-`recompute_updated`-first for the cold remainder, so a beach in active demand never loses its flag to the rotation once the table outgrows one run — gathers the fast-changing safety inputs (NWS + ECCC land alerts, ECCC marine warnings via `src/clients/ecccMarine.js`, SRF rip risk) via `src/clients/*`, gathers active water-quality advisories from the `src/wqFloor/` raise-only floor registry (one `scrape()` per matched source, folded into the estimate as `waterQualityAdvisory` — a raise-only floor that can lift a flag to yellow/red but never lower one), **reads** wave height + wind fallback from the `"waveinput:" + beachId` KV the wave cron wrote (its `model` may name a supplemental fallback source), computes estimates, scrapes official sources, writes KV `"flag:" + beachId`, `"official:" + beachId`, and `"wqfloor:" + beachId` (the last written only when an advisory is active) with `expirationTtl: 7200` — every fan-out KV write in BOTH crons goes through the bounded-concurrency pool in `src/pool.js` (`KV_WRITE_CONCURRENCY`), never a sequential per-beach `await env.FLAGS.put`; the outer per-scraper loop stays sequential because it mutates shared `scraperhealth:` state (a scraper may set an optional `officialTtlSeconds` to extend its own official-KV TTL for a reduced fetch cadence — no registered scraper declares one today; it is a retained extension point — the separate, optional `staleMs`/`readingNote` a scraper may declare ride along on the written record as display-side hints and never affect the TTL). Offset off the congested top-of-hour `:00` slot the repo's own GH workflows deliberately avoid; still **reads** (never fetches) the `waveinput:` KV the `:15` wave cron wrote, so any minute before `:15` preserves the ordering. The single national NWS `/alerts/active` fetch is matched to BOTH a beach's land `nws_zone` AND its adjacent `marine_zone` (marine warnings + Small Craft Advisory are zoned to the marine zone), merged into one alerts list — no extra upstream call; for Canadian beaches the ECCC land alerts and marine warnings are two national fetches (disjoint collections) matched per beach by region polygon and concatenated the same way.
   - `"15 */6 * * *"` (6-hourly): `runWaveRefresh` — owns ALL Open-Meteo/GLOS wave & wind fetching (marine wave batch, GLOS Seagull buoy gap-fill, then the `src/waveSources/` ordered SUPPLEMENTAL fallback registry — NWS gridpoint, NWS nearshore-marine-forecast, UW Sea Caves, Toronto beach obs, NDBC buoys — consulted only for beaches still wave-null and never additive, then Open-Meteo wind fallback), paced under Open-Meteo's per-minute rate limit (`OPEN_METEO_CONCURRENCY` is 1: batch 100 x concurrency x 60000 / (gap + fetch) = ~400 locations/min against Open-Meteo's documented 600/min ceiling — at 2 it was ~857/min, 143% of it, and the run logged two HTTP 429s every time). Reads beaches with the same hot/cold demand-priority ordering as the hourly cron but rotates on **its own** `wave_updated` cursor (migration 0012), which it alone writes — the two crons deliberately do NOT share a cursor, because the hourly cron rewrites `recompute_updated` to one shared `nowIso` for its entire run every hour, flattening the column so the wave cron's cold-tier sort collapsed to `id ASC` and a fixed tail of the table starved forever. Steps run in order: 1 marine waves → 2 GLOS buoy gap-fill → 2b supplemental wave sources (SEQUENTIAL by design — `src/waveSources/index.js` memoizes the resolved value, not the in-flight promise, so pooling it would duplicate upstream fetches in production while every sequential dedup test stayed green) → 3 wind fallback → 3b NDBC water-temp FETCH → 4 the per-beach write pass. That write pass is a single bounded-concurrency pool (`KV_WRITE_CONCURRENCY`, `src/pool.js`) writing `"waveinput:" + beachId` (wave height + wind fallback the hourly cron reads), `"waves:" + beachId` (detail-page 24 h strip) and `"watertemp:" + beachId` — all at `expirationTtl: 25200` (7 h). The water-temp record (nearest NDBC realtime2 buoy's WTMP, deduped by station id, DISPLAY-ONLY: read by the detail page for the `.beach-subtitle` "…°F Water" fragment, never feeds `src/rules.js`, never bumps `RULES_VERSION`) is written INDEPENDENTLY of the two wave skip guards — until this pass was split and pooled it sat behind a ~1450-put sequential write loop that ate the whole 900 s invocation, so not one `watertemp:` key ever existed in production. The run is wall-clock bounded end to end (`runBudget(env)`): no new upstream work after T+480 s, a 120 s sub-budget on step 2b so it can never starve the wind fallback, and the write pool YIELDS at T+840 s rather than being SIGKILLed at 900 s. Because the cursor is stamped incrementally (in flushes of `WAVE_CURSOR_FLUSH_SIZE`, for every beach that reached a write DECISION — including the graceful-degradation skips, or a permanently-masked beach would pin the queue head forever — but never for beaches the gather deadline meant it never attempted, and never for a beach whose writes all THREW, which is counted in `failures=` instead), a truncated run persists a prefix and the rest sorts first next run. The completion log reports `truncated=` from CLOCK exhaustion (`reached < beaches` or `unattempted > 0`) and write failures separately in `failures=`, so one flaky put cannot trip the truncation alarm while a systemic write outage is unmissable. Separate/less-frequent because the marine models only publish every 6–12 h.
   - `"17 3,9,15,21 * * *"` (4x daily): NWS point enrichment — beaches with `nws_zone` NULL get `nws_zone`/`nws_grid_url` via api.weather.gov/points, 75 per run, queue ordered fewest-attempts-first then `last_viewed DESC` (recently-viewed beaches drain their zone gap first) then `RANDOM()`.
   - `"29 4,10,16,22 * * *"` (4x daily): ECCC zone enrichment — Canadian beaches NWS enrichment permanently parked get `eccc_zone` (public forecast region NAME) via the GeoMet API, 50 per run, same fewest-attempts/`last_viewed DESC`/`RANDOM()` queue order as NWS enrichment. ONE bulk `fetchEcccForecastZones()` polygon fetch per run + local point-in-polygon (`ecccZoneNameForPoint`), not per-beach GeoMet lookups; a failed bulk fetch parks the whole run.
   - `"31 9 * * *"` (daily): Windy webcam hydration, 100 lookups per run (due beaches on the same coarse grid cell share ONE bbox `/webcams` request; lone/cap-truncated/failed buckets fall back to per-beach nearby queries), queue ordered never-checked-first, then `last_viewed DESC` as a demand tiebreak within each of never-checked/due-for-recheck, then oldest-checked-first.
   - (`beaches.marine_zone` is NO LONGER an in-Worker cron — the old `"23 1,7,13,19 * * *"` marine-enrichment probe was retired and moved to the offline discovery batch; see the Offline path.)
3. **Offline path** (GitHub Actions, `scripts/discovery-batch.js` on Deno, NOT in the Worker): beach discovery + water-body classification run SOLELY here. Discovery and classification are **split into two independent workflows** so a slow classification pass can never starve the fast, delete-bearing discovery pass:
   - **Discovery** (`.github/workflows/discovery.yml`, daily `"47 8 * * *"`, concurrency group `discovery`): runs `discovery-batch.js --no-classify --marine-zones data/marine-zones-greatlakes.json` = Overpass tiling → beach upserts + stale-row reconciliation (the ONLY delete path) + `flag_history` retention + `sync_meta`. Named upserts are DECOUPLED from reconciliation: the named loop is best-effort — a partial named fetch still emits idempotent UPSERTS for every tile that fetched, while reconciliation/DELETE runs ONLY under provably-complete coverage via the pure `reconciliationAllowed(namedComplete, parkComplete)` gate (any failed/skipped/budget-stopped tile makes `namedComplete` false). Park tiles are fetched only when the named pass completed (deletes are off otherwise). A total outage fast-defers (the `shouldFastDefer` circuit breaker at 3 failed / 0 ok, the post-loop 0-ok defer, or the 90-min wall-clock budget) exiting 1 so Apply skips; `sync_meta` records a `last_overpass_complete` marker alongside `last_overpass_count` so a partial run's smaller count isn't misread as a shrink. This run ALSO derives `beaches.marine_zone` OFFLINE (`--marine-zones`), replacing the retired in-Worker marine-enrichment probe: a pure local nearest-marine-zone pass (point-in-polygon + nearest-edge, 15 km cap — a strict superset of the old probe's ~13.6 km reach) over the snapshot against the repo-committed `data/marine-zones-greatlakes.json` (`src/marineZones.js`), only for US beaches with `nws_zone` set, emitting change-only idempotent UPDATEs with ZERO upstream requests, never touching the delete path. That JSON is regenerated ~biannually with `scripts/build-marine-zones.js` when NWS publishes a new coastal marine-zone shapefile (https://www.weather.gov/gis/MarineZones).
   - **Classification** (`.github/workflows/classify.yml`, hourly `"23 * * * *"`, concurrency group `classify`): runs `discovery-batch.js --no-discovery --classify-limit 25` = classify-only (NO Overpass tiling, NO upserts, NO reconciliation, NO deletes) — emits ONLY `water_class` UPDATEs, 25 beaches/run (lowest-attempts-first, ~600/day, same throughput as the old 4x-daily 150/run cadence in shorter, politer Overpass bursts; manual `workflow_dispatch` runs default to 150 for bulk drains), draining the queue over repeated runs. Once the backlog drains, most hourly runs emit zero UPDATEs — the delta-summary step guards `grep -c` against pipefail so a no-op run stays green. A COMPLETE Overpass probe always DECIDES: `classifyWaterBody` classifies a clean-but-empty result (no coastline, no allowlisted lake relation, no qualifying water way in range) as `inland` rather than leaving the row NULL, so only a transient failure leaves a row unclassified and `bumped` should read 0 in every run log. This matters because `FLAG_WORTHY_WATER_SQL` is deliberately fail-OPEN for NULL rows under the attempts cap — an unclassified beach is served live with an estimated flag card, so leaving away-from-water beaches pending for all 5 attempts published inland-lake beaches for ~5 hours each (the Locklin Pines regression). The queue also carries a ONE-TIME legacy re-drain for rows parked unclassified by the old behavior (`water_class_version IS NULL AND water_class IS NULL AND water_class_attempts >= 5`), admitted despite the cap but WITHOUT resetting attempts, so they stay hidden while they re-decide; a `WATER_CLASS_VERSION` bump cannot reach them because the version clause is ANDed with the cap. Distinct concurrency group from discovery so the two can run concurrently — they touch disjoint columns. Classify also passes `--classify-budget-ms` (a 60-min wall-clock cap, below the 90-min job timeout) and flushes each `water_class` UPDATE to the delta file incrementally, so a run cancelled by an Overpass 504 storm still persists the beaches it finished: the budget makes the run exit 0 (Apply runs on its normal gate), and Upload+Apply are `always()`-gated (a `timeout-minutes` cancel would SKIP `!cancelled()` steps) with Apply truncating any torn SIGKILL tail and an empty/partial delta applying as an idempotent no-op. The two-path invariant (request path reads only D1/KV) is unchanged.

   `discovery-batch.js` takes `--no-classify` (discovery-only), `--no-discovery` (classify-only), and `--marine-zones <path>` (the offline marine_zone pass, which either mode may also carry); the `nothingToDo` guard errors only when discovery, classify, AND the marine pass are all off. The batch reuses the discovery/classification code verbatim (`src/discovery.js`, `src/clients/overpass.js`, `src/waterClass.js`), tiles each region in `src/regions.js` (the Great Lakes coastal region set) at `TILE_MAX_SPAN_DEG = 2.0`, scopes reconciliation delete-candidates by `pointInAnyRegion`, emits one idempotent `.sql` delta, and bulk-loads it into D1 via `wrangler d1 execute --remote --file`. Overpass is hardened against public-mirror 504 overload: the named-beach query runs at `[timeout:90]` under a tighter `OVERPASS_NAMED_TIMEOUT_MS` transport cap, and per-tile fetches retry with bounded exponential backoff + jitter (`OVERPASS_TILE_ATTEMPTS=3`). Same two-path invariant: both workflows write D1 out-of-band and the request path still reads only D1/KV. See `docs/offline-discovery.md` for the design.

### The Worker entry module (`src/index.js`)

workerd treats **every named export of the entry module as a potential entrypoint** and rejects any that is not a function or an `ExportedHandler`. A single `export const FOO = 123` there kills the whole Worker at startup:

```
Uncaught TypeError: Incorrect type for map entry 'FOO': the provided value is not of type 'function or ExportedHandler'.
```

Nothing in CI sees this — the module imports fine under vitest, and `wrangler deploy --dry-run` only bundles, never boots the runtime — so it surfaces at `npm run dev` or on a real deploy. Shared constants belong in their own module that `src/index.js` imports (`src/demandWindow.js` is the precedent); function exports for tests are fine. `test/workerExports.test.js` guards this.

### Platform limits that actually bind

Design the crons against these, not against intuition — each one has already invalidated a plausible-looking plan here:

- **15 minutes wall clock per cron invocation.** CPU is *not* the binding constraint: the wave run that died was 899,989 ms wall against 346 ms CPU. It is almost entirely idle waiting, so budget wall time, not work.
- **~6 simultaneous open connections per invocation**, with KV `get`/`put` counting toward it. A pool of 12, 25 or 50 all deliver ~6 in flight — size concurrency math at 6 or the arithmetic is fiction (`KV_WRITE_CONCURRENCY` requests 12 for headroom, not throughput).
- **KV: 1,000 operations per invocation is documented** but demonstrably not enforced — this Worker has long exceeded it hourly without error. Treat it as watched-not-bounded; the wave cron's `failures=` field is the trip-wire if that ever changes.
- **Open-Meteo: 600 locations/min** (plus 5,000/h, 10,000/day). `OPEN_METEO_CONCURRENCY` is 1 to stay at ~400/min; at 2 it ran ~857/min and logged two HTTP 429s every run.
- Every upstream call must pass `timeoutMs` — see "Error isolation" below.

### Reading production logs

`wrangler tail` is **live-only**, so it cannot see a cron that already ran. For anything historical use the observability API (this is how the wave-cron wall-clock kill was diagnosed):

```bash
set -a && . ./.dev.vars && set +a
ACC=0e01552527359dfcce6edc27ebedb530
curl -s -X POST "https://api.cloudflare.com/client/v4/accounts/$ACC/workers/observability/telemetry/query" \
  -H "Authorization: Bearer $CLOUDFLARE_TOKEN" -H "Content-Type: application/json" \
  -d '{"queryId":"q","timeframe":{"from":<ms>,"to":<ms>},"parameters":{"datasets":["cloudflare-workers"],
       "filters":[{"key":"$workers.scriptName","operation":"eq","value":"swim-report","type":"string"}],
       "limit":100},"view":"events"}'
```

Two things that are easy to get wrong: **always filter on `$workers.scriptName`** or you get other Workers in this account (their cron triggers look like ours and will mislead you), and use `"view":"invocations"` rather than `"events"` to see `outcome` / `wallTimeMs` / `cpuTimeMs` — `outcome: "exceededWallTime"` is invisible in the events view. A run whose completion log line is simply *absent* was killed; that absence is itself the signal.

### Single source of color

`src/rules.js#estimateFlag(inputs)` is the **only** place an estimated flag color is decided. It is pure and versioned (`RULES_VERSION`): structured inputs in, complete flag object out (`color`, `reason`, `rules_version`, `official: false`, `sources`, `updated`); no fetch, no `Date.now()` (timestamp passed in). Precedence: NWS alerts (`ALERT_PRECEDENCE`, red/double-red warnings that short-circuit — Tornado Warning / High Surf Warning / marine Storm Warning → double-red; Severe Thunderstorm Warning / Beach Hazards Statement / High Surf Advisory / Rip Current Statement / High Wind Warning / marine Gale Warning / marine Special Marine Warning / Lakeshore Flood Warning / Coastal Flood Warning → red — double-reds MUST precede reds in the list since the first match wins regardless of color) → ECCC alerts for Canadian beaches (`ECCC_ALERT_PRECEDENCE`, lowercase `alert_name_en` strings; tornado warning / storm surge warning / marine storm warning → double-red; squall warning / waterspout warning / severe thunderstorm warning / marine gale warning / wind warning → red; watches deliberately unmapped) → SRF rip-current risk (HIGH → red, MODERATE → yellow) → wave height (≥4 ft red, ≥2 ft yellow, else green) → wind fallback (only when all wave models null) → unknown (gray, honest). After that, an NWS yellow WATCH/ADVISORY (`NWS_FLOOR_PRECEDENCE` — Tornado/Severe Thunderstorm/High Wind Watch, Wind/Lake Wind/marine Small Craft/Lakeshore Flood/Coastal Flood Advisory) applies as a yellow FLOOR (step 6, trigger `nws-floor`) — raising a green/unknown estimate to yellow but never downgrading a higher color — so a yellow alert can never mask a wave-height red (the same masking concern that keeps ECCC watches unmapped, resolved for NWS by flooring). Step 6b is the Canadian mirror: `ECCC_FLOOR_PRECEDENCE` (`strong wind warning`, `marine weather advisory` — ECCC's below-gale marine products) applies the same raise-only yellow floor with trigger `eccc-floor`. Then step 7 applies the raise-only water-quality floor (trigger `wq-floor`, worst-of by `SEVERITY_RANK`). The sole exception is `src/officialSources/` reporting a *scraped official* color. Any rule/threshold change requires bumping `RULES_VERSION` and updating the tests plus README's rules table.

### Error isolation

Every client in `src/clients/` returns data-or-`null` and never throws across its module boundary; the cron isolates per-beach/per-zone failures so one bad upstream never poisons the batch. The three alert clients (`nws.js`, `eccc.js`, `ecccMarine.js`) share the pure match/dedupe walk in `src/clients/alertMatch.js` (`matchedAlerts` + `pickIsoString`); `matchedAlerts` deliberately does NOT wrap the caller's match predicate in a try/catch — only `ecccMarine` catches, INSIDE its own predicate closure, so the other two still propagate a genuine throw instead of silently dropping alerts. No client's data-or-`null` boundary changed. All api.weather.gov requests must send the `User-Agent` header (`NWS_USER_AGENT` in `src/clients/nws.js`); api.weather.gc.ca (ECCC GeoMet, `src/clients/eccc.js`) needs no auth but the MSC usage policy recommends a meaningful User-Agent, so every GeoMet request now sends `ECCC_USER_AGENT`. Open-Meteo marine data commonly returns null/masked cells on the Great Lakes — treat null wave data as normal, not an error.

**Every upstream call must pass `timeoutMs`.** `src/clients/http.js` arms its `AbortController` ONLY when `timeoutMs > 0`, so a call site that omits it is genuinely unbounded — and a wall-clock deadline cannot save it, because deadlines are checked BETWEEN units of work, never inside a pending fetch. One hung socket then runs a cron to the 900 s scheduled ceiling and kills it mid-run. Current budgets: `NWS_TIMEOUT_MS` 45 s (the shared `fetchNwsJson` wrapper, so every api.weather.gov request), `ECCC_TIMEOUT_MS` 45 s (both GeoMet bulk collections, re-exported to `ecccMarine.js`), `OPEN_METEO_TIMEOUT_MS` 30 s, 15 s for the per-beach supplemental wave sources, and `GLERL_CATALOG_TIMEOUT_MS` 45 s / `GLERL_OBS_TIMEOUT_MS` 15 s (the catalogs are multi-megabyte and the timer bounds the whole body, not just headers). Anything routed through `fetchText` in `src/officialSources/util.js` is already bounded by its unconditional 30 s default.

### Frontend

`src/frontend/render.js` renderers are pure string builders: data (including a `now` timestamp) in, complete HTML out — no fetching, no Date access. Web Awesome Pro loads via the version-pinned CDN kit (`WA_KIT_BASE`, matter theme + mild palette, matching `wa-theme-matter wa-palette-mild` classes on `<html>`); font-token overrides live in `WA_THEME_OVERRIDES` (system font stacks, no webfont downloads). Font Awesome icons resolve via `data-fa-kit-code` on `<html>`. Theme edits in the kit builder do not auto-apply — the pinned CDN files are immutable; re-copy changed snippet values into `render.js`. Non-negotiable UI invariants: footer disclaimer ("Estimated — not the official flag status…") on every page, stale-data warning when `updated` is older than 2 h by DEFAULT (`STALE_MS`) — overridable per official record by the scraper's optional `staleMs`, with an optional neutral `readingNote` callout for point-in-time readings between 2 h and `staleMs` (the warning always wins over the note, the ESTIMATE card always uses the plain 2 h default, and the wave strip keeps its own 8 h `WAVE_STALE_MS`), gray/honest `unknown` (never a green default), official-vs-estimated visual distinction.

The Web Awesome component/design skills are bundled in the repo at `node_modules/@web.awesome.me/webawesome-pro/dist/skills/{webawesome,webawesome-design}/SKILL.md` — read them before writing or styling frontend markup.

### Adding an official-source scraper

Implement the scraper contract from PLAN.md (`matches(beach)` + `scrape()` returning `{color, official: true, source, updated}` or `null` on any failure) in `src/officialSources/`; a scraper may also declare the optional `staleMs` (per-source staleness horizon for the UI) / `readingNote` (neutral point-in-time note shown between 2 h and `staleMs`) / `officialTtlSeconds` (longer official-KV TTL) fields, register it in the `scrapers` array in `src/officialSources/index.js`. Parse defensively — a markup change on the source site must degrade to `null`, never a wrong color. README has the full how-to.
