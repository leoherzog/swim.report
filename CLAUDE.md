# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm test` — run the full Vitest suite
- `npx vitest run test/rules.test.js` — run a single test file
- `npm run dev` — local dev server (`wrangler dev`; `predev` auto-applies migrations to local D1). It starts with an empty local database; populate it with `npm run seed`.
- `npm run seed:layers` — download and verify the FlatGeobuf layer set into `./.layers` (`deno run --allow-net --allow-read --allow-write scripts/fetch-layers.js --dest ./.layers`). It pins one `layers/current.json` build id, sha256-verifies every layer against the build manifest, and writes the `report.json` the delete-path gate reads. Run it once per layer build, not on every seed.
- `npm run seed` — populate local D1 from that layer set (`deno run --allow-read --allow-write scripts/discovery-batch.js --layers ./.layers --out ./.seed.sql && node scripts/apply-local-sql.js ./.seed.sql`). Note the permission set: no `--allow-net`. Discovery, park association, classification and reconciliation are pure local math over those bytes, so any `--allow-net` on a `discovery-batch.js` invocation is a leftover upstream call, findable by one grep. The apply splits the delta into <90 KB line-aligned chunks, because `wrangler d1 execute --local --file` hands the whole file to workerd as one SQL call capped at 100,000 bytes (`SQLITE_TOOBIG`); the workflow's `--remote` apply uses the D1 import API and is unaffected. `scripts/build-wave-sql.js` emits the same one-statement-per-line shape and goes through the same applier.
- `npm run seed:enrich` (NWS point enrichment, up to 400 beaches per 780 s run — repeat to drain the queue), `seed:eccc`, `seed:webcams`, `seed:watertemp`, `seed:flags` and `seed:alerts` trigger the matching crons. `npm run seed:marine` is not a cron trigger: it snapshots local D1, runs `discovery-batch.js --no-discovery --no-classify --marine-zones data/marine-zones.json --snapshot <file>`, and applies the delta through `apply-local-sql.js`. Run it after `seed:enrich` has stamped `nws_zone`, since the pass only derives zones for rows that already have one.
- The wave pipeline is three local steps, mirroring the `seed:layers` / `seed` split. `npm run seed:wavegrids` downloads one NOAA GRIB2 cycle into `./.wavegrids` (`fetch-wave-grids.js`, the only `--allow-net` script in the pipeline). `npm run seed:waveplanes` runs GDAL: a `gdalinfo -json` sidecar per file, `sample-waves.js --mode plan` to resolve which band carries each hour's HTSGW and WIND, then one `gdal_translate` per band into a flat ENVI plane. `npm run seed:waves` samples every beach, applies the build gate, emits `./.wavesql/wave-delta.sql` and applies it through `node scripts/apply-local-sql.js`. GDAL runs only in the shell, so no Deno script in the pipeline carries `--allow-run`. Run `seed:waves` before `seed:flags`.
- **Every `deno` invocation in this repo must set `DENO_NO_PACKAGE_JSON=1`** — every `npm run` script above does, and so must every `deno` step in every workflow. The repo-root `deno.lock` is auto-discovered for all Deno commands here, and without that env var Deno folds `package.json`'s npm dependency tree into the lockfile it expects: `deno check --frozen` then fails with "The lockfile is out of date", and a plain `deno run` silently rewrites the checked-in lock. The fix is the env var, never regenerating the lock without it. `deno.json` carries exactly two things: `nodeModulesDir: "none"`, so the batch resolves flatgeobuf from the npm cache rather than a CI-absent `node_modules/`; and the import-map entry `"flatgeobuf/": "npm:/flatgeobuf@4.4.0/"`, whose leading slash after `npm:` is the canonical Deno form for a trailing-slash directory mapping. That lets `scripts/lib/fgbReader.js` use a bare specifier both Deno and vitest resolve, where an `npm:` URL would be unloadable under vitest.
- Cron triggering in local dev goes through `/cdn-cgi/handler/scheduled?cron=<urlencoded cron>`.
- `npm run deploy` — deploy (`wrangler deploy`); `npx wrangler deploy --dry-run` validates config without deploying.
- `npx wrangler d1 migrations apply swim-report --local` / `--remote` — apply `migrations/` to D1.
- There is no `wrangler login` session on this machine. Export `CLOUDFLARE_API_TOKEN` before any wrangler command that talks to the Cloudflare API — see Credentials for which token.

## Production

Live at **https://swim.report** (custom-domain route). `wrangler.toml` carries the real D1/KV IDs plus observability, Smart Placement and a pinned `compatibility_date`. It also declares `[assets] directory = "public"` — the committed brand files (favicon.svg, apple-touch-icon.png, icon-192/512.png, manifest.webmanifest, og/*.png, regenerated by `node scripts/build-brand-assets.js`) are served by the platform ahead of the Worker, carrying the security headers the hand-written `public/_headers` declares; the Worker's own responses get the same four from `withSecurityHeaders` (`src/securityHeaders.js`), applied in `src/index.js` after the error boundary. There is deliberately no assets *binding*, so no module in `src/` can read one, and `not_found_handling` stays at its default so every unmatched path still reaches `handleRequest`. The `WINDY_WEBCAM_API_TOKEN` Worker secret is set. Remote data populates through the crons and the GitHub Actions pipelines only; the request path serves whatever D1 and KV currently hold.

`npm install` needs both `WEBAWESOME_NPM_TOKEN` and `FONTAWESOME_NPM_TOKEN` exported in the environment (values in `.dev.vars`, which is gitignored). `.npmrc` routes `@web.awesome.me`/`@awesome.me` and `@fortawesome` through private registries via `${VAR}` placeholders; never hardcode a token in `.npmrc`.

### Credentials

Four scoped Cloudflare credentials, no shared account token. Each job holds the narrowest scope that lets it work.

- `CLOUDFLARE_D1_EDIT_TOKEN` — repo secret, read by `discovery.yml` for the remote D1 snapshot and delta apply, and by the `waves.yml` publish-d1 job for its wave delta. Neither job holds R2 keys.
- `CLOUDFLARE_D1_READ_TOKEN` — repo secret, read by the `waves.yml` sample job for its read-only beach snapshot. That job holds no write token, so the sampler cannot write.
- `CLOUDFLARE_R2_ACCESS_KEY` / `CLOUDFLARE_R2_SECRET_ACCESS_KEY` — repo secrets, the S3-API pair both publishers use against the `swim-report` bucket.
- `CLOUDFLARE_WORKERS_EDIT_TOKEN` — lives in `.dev.vars` only and is deliberately never a repo secret, so no CI job can change the code running at swim.report. Export it as `CLOUDFLARE_API_TOKEN` for a local deploy, secret write or tail. It is not authorized for D1 (code 7403); a remote migration or `d1 execute --remote` takes `CLOUDFLARE_D1_EDIT_TOKEN` (or the read token for a SELECT).

### Inspecting wave records in production

Both queries are SELECTs, so they take `CLOUDFLARE_D1_READ_TOKEN` exported as `CLOUDFLARE_API_TOKEN`. `CLOUDFLARE_WORKERS_EDIT_TOKEN` is refused for D1 with code 7403.

One beach's stored record and its lease:

```bash
npx wrangler d1 execute swim-report --remote \
  --command "SELECT wave_expires, wave FROM beach_state WHERE beach_id = 'osm-node-1234'"
```

Whether a cycle landed, across the whole table:

```bash
npx wrangler d1 execute swim-report --remote \
  --command "SELECT COUNT(*) FROM beach_state WHERE wave IS NOT NULL AND wave_expires > unixepoch()"
```

## Architecture

Single Cloudflare Worker (`wrangler.toml`, modules syntax) that **estimates** beach hazard flag status (green / yellow / red / double-red / unknown). The core product constraint: estimated conditions must never be presentable as official flag status — every payload carries `official: true|false` and the UI renders the two distinctly.

**PLAN.md is the authoritative contract** — D1 schema, KV shapes, module signatures, rules precedence, reason-string formats. Update it when changing any cross-module interface. README.md documents the public API and rules table; TODO.md tracks known gaps.

### The two-path rule (never violate)

1. **Request path** (`fetch` → `src/router.js` → `src/frontend/render.js`): reads **only** D1 and KV. No upstream `fetch()` may ever be reachable from here. Every rendered color comes off the `beach_state` table (migrations 0014 and 0015), selected over `BEACH_STATE_JOIN` (`src/beachState.js`) in one of two widths. A route that renders a record — the detail page, `/api/flag` — selects `BEACH_STATE_SELECT` and resolves the row through `liveBeachState(row, nowMs)`, which parses the estimate, official, wqfloor and reading blobs and reads any whose `*_expires` has passed as absent. A route that renders only a beach's display flag — the home list, `?ids=`, the nearby cards, the map features — selects `CHIP_STATE_SELECT`, the scalar mirror columns, and resolves it through `liveChipState(row, nowMs)`, so the list never ships a JSON blob for the 400 ranked rows the proximity branch discards. `/api/beaches.geojson` is one D1 statement over scalar columns, each row turned into a Feature by `mapFeatureFromRow` (`src/mapFeatures.js`), which takes the marker keyword from `displayFlag` (`src/displayFlag.js`) at read time. Every surface that shows a beach's flag — list row, nearby card, detail hero, share meta, map marker, `/api/flag`'s `display` — takes color, keyword and source from one `displayFlag` call and derives none of them, so no two surfaces can disagree or credit the wrong record. There is no degraded branch and no per-beach fallback read: D1 is the source of truth, so a D1 failure surfaces as the error boundary's 500 with no-store rather than as a silently all-unknown map. `handleDetail` adds `WAVE_STATE_SELECT` for the forecast strip and resolves it through `liveWaveRecord(row, nowMs)`, which applies the same expiry rule; the blob stays in the row past its lease, so a reader that touches `row.wave` directly would resurrect a spent cycle as a live wave height. The only KV read left on this path is `watertemp:`, a single-key get in `handleDetail`.
2. **Cron path** (`scheduled` in `src/index.js`, dispatched on `controller.cron`): all upstream fetching happens here, split across independent triggers so one upstream's failure or rate limit never starves another. Discovery, classification, `marine_zone` and wave sampling are not here — the offline pipelines own them.
   - `"7 * * * *"` (hourly): reads beaches ordered hot-first (a `last_viewed` demand stamp within `HOT_VIEW_WINDOW_MS`, 7 days, always fully covered every run) then oldest-`recompute_updated`-first for the cold remainder, so a beach in active demand never loses its flag to the rotation once the table outgrows one run. It gathers NWS and ECCC land alerts, ECCC marine warnings and SRF rip risk through `src/clients/*` (the NWS and two ECCC national fetches issued concurrently with a per-promise catch; one SRF fetch per distinct WFO, pooled under `SRF_GATHER_DEADLINE_MS`), folds in `src/wqFloor/` advisories as `waterQualityAdvisory` (raise-only: it can lift a flag to yellow or red, never lower one; one scrape per matched source, pooled under `WQ_GATHER_DEADLINE_MS`, an unreached source resolving like a failed one), **reads** wave height and wind fallback off the `beach_state` join its per-run SELECT already issues, computes estimates, scrapes official sources, and writes all four cron-owned derived records into that beach's `beach_state` row: the estimate at `estimate_expires = writeEpoch + FLAG_TTL_SECONDS` (25200, sized to the cold rotation period), the official at the same lease unless its scraper declares `officialTtlSeconds` (a longer write-time lease) or `officialMaxAgeMs` (an absolute lease anchored to the record's `updated`, resolved by the pure `officialExpiryEpoch`; `nws-omr-grr` declares the 4 h reading horizon, so its morning flag dies with its numbers and a run past the horizon writes no official), the water-quality floor at `WQFLOOR_TTL_SECONDS` (7200), and the reading (`src/officialReading.js`) at an absolute expiry 4 h past the observation instant, so a scraped morning water temperature or wave height dies four hours after it was taken no matter which run picked it up. Each column carries its own lease and each record resolves independently, so a site the source reports with no posted flag still publishes its numbers. A run that resolved no advisory, no scrape or no observation writes no field for it: the upsert is `COALESCE(excluded.<c>, beach_state.<c>)`, so the stored value is left alone and expiry stays the only retraction path. A single national NWS `/alerts/active` fetch is matched against both a beach's land `nws_zone` and its adjacent `marine_zone`, and a paginated response is read as no feed, exactly as the refresh reads it; the Canadian equivalent is two national ECCC fetches of disjoint collections, matched by region polygon. Every fan-out KV write in the cron path goes through the pool in `src/pool.js`, never a sequential per-beach `await env.FLAGS.put`; the outer per-scraper loop stays sequential because it mutates shared `scraperhealth:` state. It reads the wave record and never fetches it, gating each row on `wave_expires` through `liveWaveRecord` and then resolving it through `src/waveInput.js`, which indexes the stored 24 h series at the hour the run is estimating; a live series never falls back to its own hour-0 height and a spent one yields no wave input at all. Its upsert names neither `wave` nor `wave_expires`, in the INSERT column list or the SET list, so an hourly run can never blank or restamp a wave record. The per-beach writes are not a fan-out: `beachStateUpsertStatements` merges one descriptor per beach and `chunkStatements` collapses them into `env.DB.batch` calls of 200, applied sequentially, each in its own try/catch that adds the chunk's row count to `stateFailures` without stopping the run. There are two such flushes, and the order is load-bearing: the estimates go in as soon as the per-beach pool returns, before the scrape pass, so a run killed at the 900 s ceiling inside a scraper's fetch cannot cost the beaches it has already estimated; the officials and readings go in after it. Both COALESCE onto the same row, so a beach that produced both ends the run as one row. `flag_history` rows are then built only from the ids whose estimate chunk committed, so a history row can never claim an estimate that was not persisted. `FLAG_TTL_SECONDS` lives in `src/flagTtl.js` (the entry-module export rule), and the step-6 wave and wind reads use `Number.isFinite` so a malformed stored wave record cannot reach `rules.js` step 3's unguarded else branch as a green. Each stored estimate also carries the `estimateInputs` seal (`src/flagInputs.js`), spread on after `estimateFlag` returns from the same `signals` object the estimate consumed.
   - `"3-53/10 * * * *"` (every 10 min): `runAlertRefresh`, a recompute-and-diff alerts refresh. Three national fetches, no per-beach upstream call, no persisted diff state and no run lock: it re-estimates every live estimate against the current alerts through the hourly's own `buildAlertInputs` / `buildEstimateInputs` / `estimateFlag`, feeding the recompute the `estimateInputs` seal inside the same stored estimate so no non-alert input is ever reconstructed or lost, and writes only the rows whose payload moved once `alertsAt` and the seal are excluded from the comparison. It keeps no alert-set comparison of its own, so it cannot drift from what `rules.js` decides. It pages the beaches that hold a live estimate with a keyset on `b.id`, joining `beach_state` and filtering on `estimate_expires`, so a beach with nothing to recompute from is never read, and the walk ends only on an empty page. Authority comes from the row's own zone columns against the two feed flags: a US row needs the NWS feed, a Canadian row needs both ECCC collections, and anything else counts `skipAuthority`. Its one directional rail is `skipStaleLower`: a lowering decided from sealed inputs at or past `STALE_MS` (2 h, `src/displayFlag.js`) waits for the hourly, since age can only understate a hazard. That skip is cold-tier steady state rather than an alarm. It writes only `beach_state.estimate` and `estimate_color`, through a compare-and-set on `estimate_updated` (`estimateCasStatement`, batched at 200 and flushed per page, each batch in its own try/catch so a rejected chunk costs its own beaches one cadence and not the chunks behind it): `estimate_updated` and `estimate_expires` stay out of the SET list, so the republished estimate keeps the instant its non-alert inputs were gathered and rides the original lease, and a row the hourly rewrote between the read and the write matches nothing and counts `skipSuperseded`. That CAS is the whole race contract — no lock, no cursor, no persisted diff state — and it is also what makes writing while paging safe, since it touches only rows at or before the cursor. It must never gain a `wqfloor`, `official`, `reading`, `flag_history` or `recompute_updated` write.
   - `"15 */6 * * *"` (6-hourly): `runWaterTempRefresh`, the sole writer of `"watertemp:" + beachId`. It reads NDBC `WTMP` from the nearest station carrying `CAP_WATER_TEMP` in `src/waveSources/ndbcBuoys.js` within a 25 km cap, with a 32 KB `Range` header because the NOS water-level gauges that dominate that set publish ~1 MB realtime2 files. Display-only: the detail page shows it in the water-temperature "at a glance" tile under the hero, with its station provenance, it never feeds `src/rules.js`, and it never bumps `RULES_VERSION`. It rotates on its own `wave_updated` cursor (migration 0012). The two crons must not share a cursor: the hourly cron rewrites `recompute_updated` to one shared `nowIso` for its entire run, flattening the column so a cold-tier sort over it collapses to `id ASC` and a fixed tail of the table starves forever.
   - `"17 3,9,15,21 * * *"`: NWS point enrichment — beaches with `nws_zone` NULL get `nws_zone`/`nws_grid_url` via api.weather.gov/points, 400 selected per run and walked until `NWS_ENRICHMENT_DEADLINE_MS` (780 s, the binding limit), ordered fewest-attempts-first, then `last_viewed DESC` so recently-viewed beaches drain their zone gap first, then `RANDOM()`. A centroid over water answers with the marine zone (`isMarineZoneId`), which no land product is issued for and is never stored; the cron re-probes 16 nudged points for the land zone (nearly every ocean centroid needs this, mean ~3 probes), a row the deadline leaves unreached is untouched, and a beach with only a `marine_zone` reads `alertsCheckable` false.
   - `"29 4,10,16,22 * * *"`: ECCC zone enrichment for Canadian beaches NWS enrichment has permanently parked, 50 per run, same queue order. One bulk `fetchEcccForecastZones()` fetch per run plus local point-in-polygon (`ecccZoneNameForPoint`); a failed bulk fetch parks the whole run.
   - `"31 9 * * *"`: Windy webcam hydration, 100 lookups per run. Due beaches on one coarse grid cell share a single bbox `/webcams` request; lone, cap-truncated and failed buckets fall back to per-beach queries. Ordered never-checked-first, then `last_viewed DESC`, then oldest-checked-first.
3. **Offline path** (GitHub Actions, Deno plus native shell tools, not in the Worker): two pipelines, designed in `docs/offline-discovery.md` and `docs/offline-waves.md`. `scripts/discovery-batch.js` owns discovery, classification and `marine_zone`, fed by the twice-weekly layer build (`build-layers.yml`) and run daily by `discovery.yml`; the NOAA GRIB2 wave cycle (`waves.yml`, `"52 */6 * * *"`) is the sole producer of the wave inputs the hourly cron reads. What bites from outside those documents:

   - The batch makes no upstream data queries and runs with no network permission at all (`deno run --allow-read --allow-write`). The only offline scripts that fetch upstream data are `scripts/fetch-layers.js` and `scripts/fetch-wave-grids.js`; `scripts/snapshot-d1.js` (Node) reaches only the D1 API through wrangler, paging the beach table by `id` with a `COUNT(*)` guard so a size-capped `--json` response can never pass as a whole snapshot. GDAL runs in the workflow shell, so no Deno script carries `--allow-run`; `.github/workflows/test.yml` enforces the network half machine-side. The layers are read by the offline batch alone, so R2 is never on the request path and `wrangler.toml` deliberately has no `r2_buckets` binding.
   - `CPL_TMPDIR` must be set explicitly on the layer build's `ogr2ogr` read: an exhausted GDAL node-index temp filesystem emits a flood of "Cannot read node" and then returns an empty result with a zero exit status.
   - The R2 bucket is `swim-report`, with a hyphen. The zone is `swim.report` with a dot, and R2 answers `AccessDenied` rather than `NoSuchBucket` for a bucket a token cannot see, so the dotted form fails looking exactly like a bad secret.
   - Both publishers write an immutable per-build or per-cycle prefix and overwrite the small `current.json` pointer last, so a reader can never see a torn set. The wave cycle's prefix holds only its `manifest.json`, which the next cycle's shrink and decay gates ratio against; the NDJSON travels from the `sample` job to the `publish-d1` job as the run's `wave-cycle` workflow artifact and never leaves the run.
   - Reconciliation is the only delete path, and both it and classification run only under a verified manifest — the pure gate `reconciliationAllowed(report)` in `src/layerManifest.js` — because a partial view of OSM must never read as "gone from OSM", and must never be allowed to decide `inland`, which hides beaches. Three proportional rails sit on top: a global delete cap, a per-`REGIONS`-box delete cap, and `CLASSIFY_MAX_HIDE_FLIPS` / `CLASSIFY_MAX_HIDE_FRACTION` against mass re-classification, since a hide is invisible in the row count and no delete rail can see it.
   - A layer build is not delete-bearing: a failed or sanity-refused build leaves the previous set live, which is delete-safe because an older extract is over-inclusive. A failed or refused wave cycle writes no rows at all, so its failure mode is a flag aging out to unknown, never a stale wave height deciding a color.
   - The wave delta writes one `beach_state` row per resolved beach, each carrying an absolute `wave_expires` in epoch seconds rather than a write-time TTL, so a record expires a fixed span after the hour it describes regardless of when the job ran, and republishing an older cycle is refused by construction. The span is the record's own shape: a record carrying `startIso` + `hoursFt` gets `validStartEpoch + 86400`, because `runFlagRecompute` resolves it through `src/waveInput.js` and indexes the series at the hour it is estimating. A wind-only record is one hour-0 sample and keeps `validStartEpoch + 25200`. A row whose lease has already run out is not written at all, since it would read as absent the moment it lands. A live series never falls back to its own hour-0 `waveHeightFt` and a spent one yields no wave input at all, which is what lets one landed cycle color a day of runs.
   - gfswave's GRIB2 DRS template 5.40 is JPEG 2000 with no pure-JS decode path: decoding requires GDAL, so it is impossible inside the Worker and must never be attempted there. `noaa_nwps_sew` is template 5.0 simple packing, which GDAL reads with no special handling and which proves nothing about the JPEG 2000 driver the workflow still smoke-tests. Grid choice is constrained by `beaches.water_class`, since `noaa_glwu` is the only source for the Great Lakes, which gfswave masks entirely. Beach coordinates frequently land on masked land cells, so the nearest-wet-cell spiral is the sampling mechanism, not a fallback.
   - Four grids in ordered fallthrough, and `global.0p16` is not every ocean beach: at 0.1667 degrees it masks the sheltered inland seas whole. `noaa_nwps_sew` — the Seattle office's NWPS SWAN nest over the Salish Sea, fetched through the NOMADS filter CGI, which is its only access route — closes that gap, and sits last in `GRIDS` so it is offered only the beaches `global.0p16` could not resolve. It publishes on demand rather than on a fixed cycle, so it is deliberately outside `REQUIRED_GRID_IDS` and a missing office run degrades the cycle instead of refusing it nationwide. Like every grid outside that set, its per-grid floor and record-count ratio misses warn and degrade rather than refuse, while its `validPercent` ratio still refuses. SWAN wets and dries its shore cells with the tide, so its resolved count swings about 13% with the tidal phase at validStart, and it declares `recordCountMinRatio` 0.8 to keep that swing silent; the field stays outside `gridsDigest`. It declares `windFallback: false`: its WIND plane reads 0 m/s over land where HTSGW reads its sentinel, so a wind-only record from it would be a false calm that `rules.js` colors green.
   - `gridsDigest` covers each grid's accepted water classes and its wind-fallback flag alongside its geometry, cap and url, so adding a grid, retargeting a water class or flipping the wind fallback leaves `data/wave-floors.json` with no seeded entry for the new digest. That withholds auto-publish on every cycle, which writes no rows for any grid and ages the whole site out to unknown within a day; a human seeds the new digest from a withheld manifest before the change lands. `test/waveGateData.test.js` checks only that the committed data is structurally complete and passes on a pending entry, so the outage alarm is the scheduled withheld-publish step in `waves.yml`, which fails the run.
   - `data/marine-zones.json` (`src/marineZones.js`) drives a local nearest-marine-zone pass over US beaches that already have `nws_zone`, emitting change-only UPDATEs and never touching the delete path. Regenerate it with `scripts/build-marine-zones.js` when NWS publishes a new marine-zone shapefile.

### The Worker entry module (`src/index.js`)

workerd treats **every named export of the entry module as a potential entrypoint** and rejects any that is not a function or an `ExportedHandler`. A single `export const FOO = 123` there kills the whole Worker at startup:

```
Uncaught TypeError: Incorrect type for map entry 'FOO': the provided value is not of type 'function or ExportedHandler'.
```

Nothing in CI sees this — the module imports fine under vitest, and `wrangler deploy --dry-run` only bundles, never boots the runtime — so it surfaces at `npm run dev` or on a real deploy. Shared constants belong in their own module that `src/index.js` imports (`src/demandWindow.js` is the precedent); function exports for tests are fine. `test/workerExports.test.js` guards this.

### Platform limits that actually bind

Design the crons against these, not against intuition:

- **15 minutes wall clock per cron invocation.** CPU is *not* the binding constraint: a cron that walks the whole beach table spends almost all of it idle on upstreams and KV, so budget wall time, not work.
- **~6 simultaneous open connections per invocation**, with KV `get`/`put` counting toward it. A pool of 12, 25 or 50 all deliver ~6 in flight, so size concurrency math at 6 or the arithmetic is fiction (`KV_WRITE_CONCURRENCY` requests 12 for headroom, not throughput). Per-beach `beach_state` writes are exempt because they are not a fan-out: they collapse into `env.DB.batch` calls of 200 statements, so a 3,000-beach run costs 15 round trips rather than 3,000 connections. The hourly's wave read is exempt for the same kind of reason — it rides the SELECT the run already issues — so the budget is spent on upstreams and the water-temp cron's puts.
- **A Cron Trigger under a 1 hour interval gets 30 seconds of CPU, not 15 minutes.** Wall clock stays 15 minutes for every cron either way. So the sub-hour rule is not about CPU: it is that no cron which fans out an upstream call per beach may go sub-hourly, because that is what consumes wall clock.
- **Cron Triggers are capped at 5 per ACCOUNT on Free and 250 on Paid.** This Worker's sixth trigger is a Paid-plan dependency.
- **KV: 1,000 operations per invocation is documented** but not enforced — this Worker exceeds it hourly without error. Treat it as watched, not bounded.
- **GitHub Actions crons are skipped, not merely deferred.** A pipeline's cadence must tolerate consecutive missed occurrences, not just late ones. The wave cycle runs 4 slots a day against a 24 h absolute series lease, tolerating two consecutive misses with six hours to spare before beaches age out to unknown.
- Every upstream call is bounded: the transport wrappers arm `AbortSignal.timeout` at `timeoutMs` when a call site passes one and at `DEFAULT_TIMEOUT_MS` (30 s) otherwise — see "Error isolation".

### Reading production logs

`wrangler tail` is **live-only**, so it cannot see a cron that already ran. For anything historical use the observability API:

```bash
set -a && . ./.dev.vars && set +a
ACC=0e01552527359dfcce6edc27ebedb530
curl -s -X POST "https://api.cloudflare.com/client/v4/accounts/$ACC/workers/observability/telemetry/query" \
  -H "Authorization: Bearer $CLOUDFLARE_WORKERS_EDIT_TOKEN" -H "Content-Type: application/json" \
  -d '{"queryId":"q","timeframe":{"from":<ms>,"to":<ms>},"parameters":{"datasets":["cloudflare-workers"],
       "filters":[{"key":"$workers.scriptName","operation":"eq","value":"swim-report","type":"string"}],
       "limit":100},"view":"events"}'
```

Always filter on `$workers.scriptName`, or you get other Workers in this account, whose cron triggers look like ours. Use `"view":"invocations"` rather than `"events"` for `outcome` / `wallTimeMs` / `cpuTimeMs`: `outcome: "exceededWallTime"` is invisible in the events view. A run whose completion log line is simply *absent* was killed. A run whose `<label> failed:` line is present threw past its top level: it rejected its `waitUntil` promise and shows as an exception outcome in the invocations view rather than ok. That is the one failure the cron path does not swallow, and Cloudflare documents no retry for it. Request URLs in Workers Logs carry no query string (`redact_query_string`), so `?near=`, `?q=` and `?ids=` are not recoverable from a logged request.

### Single source of color

`src/rules.js#estimateFlag(inputs)` is the **only** place an estimated flag color is decided. It is pure and versioned (`RULES_VERSION`): structured inputs in, complete flag object out (`color`, `reason`, `rules_version`, `official: false`, `sources`, `updated`); no fetch, no `Date.now()`.

Only an alert in effect at the run instant counts (`alertsInEffect`: onset at or before it, ends after it); one published ahead of its onset rides in `alertDetails` for the hazard lane but decides nothing. Precedence, first match wins: NWS alerts (`ALERT_PRECEDENCE`) → ECCC alerts for Canadian beaches (`ECCC_ALERT_PRECEDENCE`, lowercase `alert_name_en` strings, watches deliberately unmapped) → SRF rip-current risk (HIGH red, MODERATE yellow) → wave height (≥4 ft red, ≥2 ft yellow, else green) → wind fallback, only when all wave models are null → unknown, gray and honest. Within each alert list every double-red must precede every red, since the loop takes the first match regardless of color. Three raise-only floors then apply, each able to lift a lower color but never lower a higher one: `NWS_FLOOR_PRECEDENCE`, `ECCC_FLOOR_PRECEDENCE` and the water-quality floor (worst-of by `SEVERITY_RANK`). Flooring rather than mapping is what stops a yellow alert masking a wave-height red. PLAN.md and README's rules table carry the full alert-name lists.

The sole exception is `src/officialSources/` reporting a *scraped official* color. Any rule or threshold change requires bumping `RULES_VERSION` and updating the tests plus README's rules table. `windGustMph` is permanently null because no wave grid in the set publishes a GUST element, so the wind red test is speed alone and `rules.js` renders `n/a` for the gust.

Which of a beach's two records a surface shows as its flag, and whether that flag earns the OFFICIAL badge, is decided only by `displayFlag(state, nowIso)` in `src/displayFlag.js`; the per-record estimate and official cards render their own record verbatim.

### Error isolation

Every client in `src/clients/` returns data-or-`null` and never throws across its module boundary; the cron isolates per-beach and per-zone failures so one bad upstream never poisons the batch. The three alert clients share the pure match/dedupe walk in `src/clients/alertMatch.js`, which deliberately does not wrap the caller's match predicate in a try/catch — only `ecccMarine` catches, inside its own predicate closure, so the other two still propagate a genuine throw instead of silently dropping alerts. All api.weather.gov requests must send `NWS_USER_AGENT`, and every ECCC GeoMet request sends `ECCC_USER_AGENT`. A wave model masks land, so a null wave value for a coastal point is normal rather than an error.

**Every upstream call is bounded.** `src/clients/http.js` and `fetchText` in `src/officialSources/util.js` bound every request with `AbortSignal.timeout`, at `timeoutMs` when it is a number > 0 and the shared `DEFAULT_TIMEOUT_MS` (30 s) otherwise, so no call site is unbounded; a hung request rejects with a TimeoutError and degrades to null through the same catch as any other failure. Every `src/clients/` module and every direct `fetchJson` caller outside it (`nwsOmr`, `nyOprhpBeachStatus`, `mnBeaches`) passes `timeoutMs` so the bound is visible at the site; `fetchText` callers pass none and take the 30 s default, and no registered scraper overrides it. A wall-clock deadline cannot replace it, because deadlines are checked between units of work, never inside a pending fetch, and one hung socket would otherwise run a cron to the 900 s scheduled ceiling. `NWS_TIMEOUT_MS` and `ECCC_TIMEOUT_MS` are both 45 s, covering every api.weather.gov request (the OMR scraper included) and both GeoMet bulk collections. Both wrappers release an unread non-2xx body through `cancelBody` without touching the returned status.

### Frontend

`src/frontend/render.js` renderers are pure string builders: data (including a `now` timestamp) in, complete HTML out — no fetching, no Date access. Web Awesome Pro loads via the version-pinned CDN kit (`WA_KIT_BASE`, matter theme plus mild palette, matching `wa-theme-matter wa-palette-mild` classes on `<html>`), with font-token overrides in `WA_THEME_OVERRIDES` and Font Awesome icons via `data-fa-kit-code`. The pinned CDN files are immutable, so kit-builder theme edits do not auto-apply; re-copy changed snippet values into `render.js`. The bundled Web Awesome component and design skills at `node_modules/@web.awesome.me/webawesome-pro/dist/skills/{webawesome,webawesome-design}/SKILL.md` come first when writing or styling frontend markup. `src/frontend/sun.js` delegates sunrise and sunset to the exact-pinned `suncalc` npm package, the one runtime npm import bundled into the Worker; `test/workerExports.test.js` forbids only `flatgeobuf` and the offline modules from the entry closure.

Non-negotiable UI invariants: the footer disclaimer ("Estimated — not the official flag status…") on every page; a stale-data warning when `updated` is older than 2 h by default (`STALE_MS`), overridable per official record by a scraper's optional `staleMs`, with an optional neutral `readingNote` callout for point-in-time readings between 2 h and `staleMs` (the warning always wins over the note, the estimate card always uses the plain 2 h default, and the wave strip keeps its own 8 h `WAVE_STALE_MS`); gray, honest `unknown` and never a green default; and a visible distinction between official and estimated.

### Adding an official-source scraper

Implement the scraper contract from PLAN.md (`matches(beach)` plus `scrape()` returning `{color, official: true, source, updated}`, or `null` on any failure) in `src/officialSources/`, and register it in the `scrapers` array in `src/officialSources/index.js`. A scraper's site may also carry `waterTempF` / `waveHeightFt`, the source's own point-in-time observations, resolved by `scrapeReadingFromResult` into the `beach_state.reading` record; they are display-only, never reach `src/rules.js`, and are what makes a site with a null `color` worth emitting. A scraper may also declare the optional `staleMs`, `readingNote`, `officialTtlSeconds` and `officialMaxAgeMs` fields; `officialTtlSeconds` sets `official_expires` alone and is free to run past the estimate's `FLAG_TTL_SECONDS` (25200), because every reader checks each column's lease on its own, and `officialMaxAgeMs` replaces it with an absolute lease measured from the record's `updated`, for a posting that is itself a point-in-time observation. `staleMs` is orthogonal: it governs how the renderer judges the reading's age, not how long the record lives. Parse defensively: a markup change upstream must degrade to `null`, never a wrong color. README has the full how-to.
